被吞掉的錯誤

2026-07-20 更新 — 本節原始主張已被實驗證偽

本節原先認定「錯誤被吞」是 hang 的成因。實作階段的特性化測試(各重現 3 次)證明並非如此:

目標不可達 → runConnections() 永不拋錯、永不返回。
被取消 → 正常返回,不拋任何錯誤(連 CancellationError 都沒有)。

兩種情況下都沒有錯誤存在,因此「吞錯」不可能是成因。連帶結論:改動 1 治不了 hang,它只能治連線洩漏;且生產程式碼不得以 catch is CancellationError 判斷連線是否因取消而收尾。hang 的真正成因已另案調查(見第 11 節)。

以下程式碼與說明保留,作為原始推論的紀錄 —— 這段程式碼確實仍是缺陷(無主的 Task),只是它造成的是洩漏而非 hang。

05deinit 實測

最初的修正提案是用 deinit 當安全網。實測證明:在最需要它的情境下,deinit 永遠不會觸發。

bridge task 隱式強持有 self

Subscription.swift:77 的 Task {} 沒有 capture list,卻引用了 stored property source 與 tracker —— Swift 6 允許此處的隱式 self 捕獲,因此該 Task 強持有整個 Subscription。

CASE 1: 從未存取 .events,然後丟棄 >>> deinit A ← deinit 有觸發 CASE 2: 存取 .events(bridge task 啟動)後丟棄 (無 deinit 輸出) ← deinit 永遠不觸發
這推翻了原提案的安全網

deinit 只救得了「從未迭代就丟棄」。而實際發生的 hang 正是「.events 正在被迭代」—— 此時 bridge Task 持有 self,而它正等在 source.stream 上,而 source 只有 teardown 才會結束。互相卡死。

06修正方案

四處改動,全部落在已驗證的失效路徑上。其中第 1 項是治 hang 的關鍵,2–4 項治洩漏並履行文件合約。

四處改動與各自解決的問題
#改動位置解決
1 持有 connectionTask,不再吞錯;失敗需傳遞給 RPC。completion 中額外 .cancel() StreamStream.perform 連線洩漏
2 teardown 從 lazy getter 移入 init 的 source.continuation.onTermination Subscription.init teardown 不可達
3 bridge Task 加明確 capture list,解除對 self 的強持有 Subscription.events 物件永不釋放
4 新增 deinit,作為「從未迭代就丟棄」的兜底 Subscription 連線洩漏
改動 1 的核心不變式

連線 task 必須有明確擁有者,且在 teardown 時被取消,不得無主殘留。

原先此處要求「必須使進行中的 RPC 以錯誤終止」,該要求已撤銷 —— 特性化測試證明取消 runConnections() 不產生任何錯誤,也不影響已排隊的 RPC。此要求移至第 11 節另案處理。

修正前 / 修正後 — 失敗傳遞路徑
修正前
連線死亡 → 錯誤被吞 → RPC 無限等待
teardown 由「終止」觸發
但終止永遠不會來
修正後
連線死亡 → 錯誤被觀察 → RPC 失敗
RPC 失敗 → source 終止
→ teardown 鏈完整執行
刻意不做的事

不在 SDK 加 RPC deadline。理由與測試裡不用計時相同 —— 那是一個沒人能正當決定的數字。正確行為是「連線死掉時就失敗」,而不是「等一個猜出來的時間後失敗」。第 1 項改動正是為了達成前者。

不動 UnaryUnary / StreamUnary / UnaryStream。那三條路徑本來就有 defer,且不在已驗證的失效路徑上。符合 CLAUDE.md 的 Minimal Impact 原則。

07錯誤語意

連線死亡目前對使用者是「無限靜默」。修正後應是明確且可據以續傳的錯誤。

錯誤映射
情境拋出攜帶資訊
連線 task 失敗 / 結束而 RPC 仍在等 .subscriptionDropped reason · lastRevision · lastPosition
RPC 本身被取消 .connectionClosed 維持現狀
這個 error case 一直存在,但從未被接上

KurrentError.swift:58,60 宣告了 subscriptionTerminated 與 subscriptionDropped(reason:lastRevision:lastPosition:),並在 description 有完整處理 —— 但全 Sources/ 沒有任何一處拋出它們。

subscriptionDropped 攜帶的正是 tracker 一直在維護、文件也明說「用來斷線後續傳」的 lastRevision / lastPosition。它就是為這個情境設計的,只是從未被接上。

08驗證設計

關鍵設計決定:斷言不碰時間。時間界限只存在於維運層,且不編碼任何關於 SDK 時序的假設。

為什麼斷言不能依賴計時

若測試以「N 秒內沒卡住就算過」來斷言正確性,它本身就是機率性測試 —— 等於用我們正在治療的病來當藥。而且 Swift Testing 的 .timeLimit 有硬性限制:

實測 — 在測試 target 編譯 .timeLimit(.seconds(5))
error: 'seconds' is unavailable: Time limit must be specified in minutes

最小粒度是 1 分鐘,連「數秒內失敗」都做不到。因此設計上把兩件事切開:

時間界限的歸屬 — 誰決定數字,以及憑什麼
斷言正確性 → 不碰時間
直接建構 Subscription,先同步驅動失敗,再 await。
實作正確時 stream 必定已終止,next() 立即回傳或拋出。
偵測無限卡住 → 維運上限
suite .timeLimit(.minutes(1)) + job timeout-minutes。
語意是「單元測試不該逼近一分鐘」,非 SDK 時序假設。
誠實限制

「永遠不會終止」在原理上無法不用時間界限來偵測。這裡能做的是把界限推到它該在的位置(維運政策),而不是讓它出現在斷言裡。最差情況下回歸了,也是 1 分鐘失敗且其他 cell 照跑完,而非 16 分鐘靜默加整個 matrix 陪葬。

契約測試 — 確定性,不需伺服器

Subscription.init(writer:)、send(state:)、onFinish(_:) 皆為 internal,測試可用 @testable import KurrentDB 直接建構並驅動。MockKurrentDBClient 幫不上忙 —— 它只是 factory 呼叫的 spy,不模擬 gRPC 傳輸。

屆時必須處理的四個問題

先記錄於此以免遺失 —— 這些在核心修好之後仍然存在。

1
subscriptionId 每次重連都會變
由伺服器 .confirmation 訊息提供(Subscription.swift:118-119);而 ack(eventIds:)(line 135)在呼叫當下才讀取它 → 重連後 ack 斷線前的事件會送往新 subscription
2
writer 需重新綁定
teardown 會 writer.stop()。重連若未處理 writer 重綁,ack 會靜默送進虛空
3
重複事件的可見性
持久訂閱為 at-least-once,重連本就會重送未 ack 事件。若重連完全透明,使用者看到重複時無從得知原因
4
可重用既有基礎設施,但預設值不適用
OperationRetryPolicy(含指數退避與 jitter)、withRetry、isNodeFailure 皆可沿用。但 .default 為 3 次嘗試,係為一次性操作設計,不適用於長生命週期訂閱
對本設計的約束

本設計不得阻擋該層。改動 1 使連線死亡成為可觀察事件,正是重連所需的觸發點 —— 兩者方向一致,不衝突。

11hang 另案調查

原假設已證偽。本節記錄目前排除了什麼、以及最有力的候選。

已排除的成因
錯誤被吞
兩種情境下皆無錯誤產生 —— 無錯可吞
目標不可達
CI 的 Wait for cluster to be healthy 已通過,叢集是健康的
最有力的候選:CallOptions.waitForReady

grpc-swift 的文件(CallOptions.swift:44)寫著:「若為 false,連線發生暫時性失敗時 RPC 會立即中止;否則 gRPC 會持續嘗試連線,直到 deadline 被超過。」

本 SDK 既未設定 waitForReady,也未設定任何 deadline。兩者相加即為:連線一有問題,RPC 便無限等待 —— 與觀察到的靜默 hang 吻合,且不需要伺服器不可達,只需要一次連線抖動。

為何未納入本次修正:這是全域行為變更(影響所有 RPC,非僅訂閱),且「它就是 CI 那次 hang 的成因」目前仍屬推論。依本文一貫原則,未驗證的因果不寫進修正。

下一步驗證路徑
寫特性化測試
叢集健康但連線中途中斷 / 被重置
觀察 RPC 是否無限等待
若是,即重現了 CI 情境
驗證 waitForReady = false
是否使其立即失敗
與自動重連的關係

若 waitForReady = false 確為正解,它同時也是第 10 節自動重連所需的斷線訊號 —— 兩者應一併設計,而非各做各的。
