Results量測結果

p50 is the median wall clock per iteration; Malloc the heap allocations per iteration; Instructions the CPU instructions per iteration (macOS only: Linux needs perf_event, which GitHub runners do not expose). Lower is better everywhere. On Linux the benchmark runtime interposer adds a fixed floor of 16 allocations to every benchmark, so a zero-allocation benchmark reports 16 there.

p50 是每次迭代 wall clock 的中位數；Malloc 是每次迭代的堆積配置次數；Instructions 是每次迭代的 CPU 指令數（僅 macOS：Linux 需要 perf_event，GitHub runner 不開放）。所有數字都是越低越好。Linux 上 benchmark runtime 的 interposer 會對每個 benchmark 固定多算 16 次配置，所以零配置的 benchmark 在 Linux 會顯示 16。

Append request encodingAppend 請求編碼

Append/encode-request/<events>x<payload> builds the request messages of one append (requestMessages()) and serialises each to bytes, as the gRPC serializer does before writing them to the stream. The events carry raw Data payloads, so JSON encoding is not included.

Append/encode-request/<筆數>x<payload> 建出一次 append 的請求訊息（requestMessages()），再把每則序列化成 bytes，跟 gRPC serializer 寫進 stream 前做的事一樣。事件用的是原始 Data payload，所以不含 JSON 編碼。

Read response decoding讀取回應解碼

Read/decode-response/<events>x<payload> parses one serialised ReadResp per event, as the server streams them, and turns each into a Streams.ReadResponse. Read/decode-model/<events> then decodes the RecordedEvents of such a read into a three-field Codable struct with decode(to:).

Read/decode-response/<筆數>x<payload> 依 server 串流的方式，每筆事件解析一則序列化的 ReadResp，再轉成 Streams.ReadResponse。Read/decode-model/<筆數> 接著用 decode(to:) 把這些 RecordedEvent 解碼成三個欄位的 Codable struct。

Client stack against an in-process serverClient stack（接 in-process server）

Client/* runs a real KurrentDBClient against an in-process server (Benchmarks/OfflineBenchmarks/InProcessServer.swift), plugged in through the package-level ClientSettings.transportProvider. Node selection, the retry wrapper, the shared connection, the generated gRPC client and the response sequences run as they do against a node. The server answers from responses serialised in advance and never parses a request, and there are no sockets and no HTTP/2 framing, so what is left is the cost of the client and of grpc-swift. GRPC/* makes the same calls with the generated gRPC client alone on the same kind of connection: Client/* minus GRPC/* is what the SDK adds. Both include one copy of every message between the in-process transport's [UInt8] and the Posix transport's bytes type (one allocation per message), which a real connection does not make. Measured on the commit that added them; Linux in run 40168799307 (Intel Xeon Platinum 8573C, 4 vCPU).

Client/* 用真的 KurrentDBClient 接 in-process server（Benchmarks/OfflineBenchmarks/InProcessServer.swift），透過 package 層級的 ClientSettings.transportProvider 接上。node 選擇、retry、共用連線、生成的 gRPC client 與回應序列都跟接真 node 時一樣在跑。server 用事先序列化好的回應作答，從不解析請求；沒有 socket、也沒有 HTTP/2 framing，所以剩下的就是 client 與 grpc-swift 本身的成本。GRPC/* 在同樣的連線上只用生成的 gRPC client 做同樣的呼叫：Client/* 減掉 GRPC/* 就是 SDK 多出來的部分。兩者都包含每則訊息在 in-process transport 的 [UInt8] 與 Posix transport 的 bytes 型別之間複製一次（每則一次配置），這是真連線不會有的。量測於加入它們的 commit；Linux 為 run 40168799307（Intel Xeon Platinum 8573C, 4 vCPU）。

Method量測方法

The suite is Benchmarks/OfflineBenchmarks, built with ordo-one/benchmark in release mode. The Benchmarks workflow runs it on ubuntu-latest on every push to main, publishes the markdown report to the job summary, and uploads two measures per benchmark to Bencher: latency (p50 wall clock in ns, bounds p0/p90) and the p50 malloc count, as allocations or, for the client-stack benchmarks, allocations-concurrent. On a push to main two thresholds can fail the run: a t-test on latency (upper boundary 0.99 over the last 64 runs, once a benchmark has 10) when the result lands outside the band of recent history, and a percentage test on allocations (upper boundary 1% against the previous run) when the count grows by more than 1%. Allocation counts are deterministic for a given toolchain and runner image, so growth comes from a code change, a new Swift patch release or a new runner image; each alerts once, and the next run compares against the new count. The client-stack benchmarks are the exception: they allocate on several concurrent tasks, and on the 4-vCPU runner a lazy read's count per iteration spreads over about 10%, so allocations-concurrent keeps their history without a threshold and the latency test covers them.

套件是 Benchmarks/OfflineBenchmarks，用 ordo-one/benchmark 以 release 模式建置。Benchmarks workflow 每次 push 到 main 就在 ubuntu-latest 執行，把 markdown 報表寫進 job summary，並對每個 benchmark 上傳兩個 measure 到 Bencher：latency（p50 wall clock，單位 ns，區間 p0/p90）與 p50 配置次數；配置次數一般記為 allocations，client stack 的 benchmark 記為 allocations-concurrent。push 到 main 時有兩個門檻會讓執行失敗：latency 上的 t-test（最近 64 次、上界 0.99，累積滿 10 次才開始）在結果落在歷史區間外時觸發；allocations 上的 percentage 門檻（對前一次、上界 1%）在配置次數增加超過 1% 時觸發。同一套 toolchain 與 runner image 上的配置次數是固定的，所以增加只會來自程式碼變更、新的 Swift patch 版本或新的 runner image；每種情況只會觸發一次，下一次執行就以新的次數為基準。client stack 的 benchmark 是例外：它們在多個並行的 task 上配置記憶體，在 4 vCPU 的 runner 上 lazy read 每次迭代的配置次數分散約 10%，所以 allocations-concurrent 只保留歷史、不設門檻，由 latency 的門檻把關。
