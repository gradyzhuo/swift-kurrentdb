Results量測結果

p50 is the median wall clock per iteration; Malloc the heap allocations per iteration; Instructions the CPU instructions per iteration (macOS only: Linux needs perf_event, which GitHub runners do not expose). Lower is better everywhere. On Linux the benchmark runtime interposer adds a fixed floor of 16 allocations to every benchmark, so a zero-allocation benchmark reports 16 there.

p50 是每次迭代 wall clock 的中位數；Malloc 是每次迭代的堆積配置次數；Instructions 是每次迭代的 CPU 指令數（僅 macOS：Linux 需要 perf_event，GitHub runner 不開放）。所有數字都是越低越好。Linux 上 benchmark runtime 的 interposer 會對每個 benchmark 固定多算 16 次配置，所以零配置的 benchmark 在 Linux 會顯示 16。

Append request encodingAppend 請求編碼

Append/encode-request/<events>x<payload> builds the request messages of one append (requestMessages()) and serialises each to bytes, as the gRPC serializer does before writing them to the stream. The events carry raw Data payloads, so JSON encoding is not included.

Append/encode-request/<筆數>x<payload> 建出一次 append 的請求訊息（requestMessages()），再把每則序列化成 bytes，跟 gRPC serializer 寫進 stream 前做的事一樣。事件用的是原始 Data payload，所以不含 JSON 編碼。

Read response decoding讀取回應解碼

Read/decode-response/<events>x<payload> parses one serialised ReadResp per event, as the server streams them, and turns each into a Streams.ReadResponse. Read/decode-model/<events> then decodes the RecordedEvents of such a read into a three-field Codable struct with decode(to:).

Read/decode-response/<筆數>x<payload> 依 server 串流的方式，每筆事件解析一則序列化的 ReadResp，再轉成 Streams.ReadResponse。Read/decode-model/<筆數> 接著用 decode(to:) 把這些 RecordedEvent 解碼成三個欄位的 Codable struct。

Method量測方法

The suite is Benchmarks/OfflineBenchmarks, built with ordo-one/benchmark in release mode. The Benchmarks workflow runs it on ubuntu-latest on every push to main, publishes the markdown report to the job summary, and uploads two measures per benchmark to Bencher: latency (p50 wall clock in ns, bounds p0/p90) and allocations (p50 malloc count). On a push to main two thresholds can fail the run: a t-test on latency (upper boundary 0.99 over the last 64 runs, once a benchmark has 10) when the result lands outside the band of recent history, and a percentage test on allocations (upper boundary 1% against the previous run) when the count grows by more than 1%. Allocation counts are deterministic for a given toolchain and runner image, so growth comes from a code change, a new Swift patch release or a new runner image; each alerts once, and the next run compares against the new count.

套件是 Benchmarks/OfflineBenchmarks，用 ordo-one/benchmark 以 release 模式建置。Benchmarks workflow 每次 push 到 main 就在 ubuntu-latest 執行，把 markdown 報表寫進 job summary，並對每個 benchmark 上傳兩個 measure 到 Bencher：latency（p50 wall clock，單位 ns，區間 p0/p90）與 allocations（p50 配置次數）。push 到 main 時有兩個門檻會讓執行失敗：latency 上的 t-test（最近 64 次、上界 0.99，累積滿 10 次才開始）在結果落在歷史區間外時觸發；allocations 上的 percentage 門檻（對前一次、上界 1%）在配置次數增加超過 1% 時觸發。同一套 toolchain 與 runner image 上的配置次數是固定的，所以增加只會來自程式碼變更、新的 Swift patch 版本或新的 runner image；每種情況只會觸發一次，下一次執行就以新的次數為基準。
