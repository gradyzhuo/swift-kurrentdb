Results量測結果

p50 is the median wall clock per iteration; Malloc the heap allocations per iteration; Instructions the CPU instructions per iteration (macOS only: Linux needs perf_event, which GitHub runners do not expose). Lower is better everywhere. On Linux the benchmark runtime interposer adds a fixed floor of 16 allocations to every benchmark, so a zero-allocation benchmark reports 16 there.

p50 是每次迭代 wall clock 的中位數；Malloc 是每次迭代的堆積配置次數；Instructions 是每次迭代的 CPU 指令數（僅 macOS：Linux 需要 perf_event，GitHub runner 不開放）。所有數字都是越低越好。Linux 上 benchmark runtime 的 interposer 會對每個 benchmark 固定多算 16 次配置，所以零配置的 benchmark 在 Linux 會顯示 16。

  • Creating a raw EventData from Data costs about 1.1 µs on macOS with 1 allocation (the internal Data copy).
  • A Codable model adds 1 allocation to box the model; encoding is deferred until .data is read, so construction cost is almost the same as the raw case.
  • encode-codable-payload is the full JSONEncoder().encode() path and the hot path when serialising events to the wire.
  • EventData construction is 3–5× slower on Linux. Allocation counts match, so this is the cost of swift-foundation's Data and UUID on that runner, not extra work in the SDK.
  • 從 Data 建立 EventData 在 macOS 約 1.1 µs、1 次配置（內部的 Data 複製）。
  • 用 Codable model 多 1 次配置來裝箱 model；編碼延後到讀取 .data 時才發生，所以建構成本跟 raw 幾乎相同。
  • encode-codable-payload 是完整的 JSONEncoder().encode() 路徑，也是事件送上線路時的熱路徑。
  • EventData 建構在 Linux 慢 3–5 倍。配置次數一致，所以差在該 runner 上 swift-foundation 的 Data 與 UUID，不是 SDK 多做了事。

Method量測方法

The suite is Benchmarks/OfflineBenchmarks, built with ordo-one/benchmark in release mode. The Benchmarks workflow runs it on ubuntu-latest on every push to main, publishes the markdown report to the job summary, and uploads two measures per benchmark to Bencher: latency (p50 wall clock in ns, bounds p0/p90) and allocations (p50 malloc count). A t-test threshold on latency (upper boundary 0.99 over the last 64 runs) fails the run when a push to main lands outside the band of recent history.

套件是 Benchmarks/OfflineBenchmarks，用 ordo-one/benchmark 以 release 模式建置。Benchmarks workflow 每次 push 到 main 就在 ubuntu-latest 執行，把 markdown 報表寫進 job summary，並對每個 benchmark 上傳兩個 measure 到 Bencher：latency（p50 wall clock，單位 ns，區間 p0/p90）與 allocations（p50 配置次數）。latency 上的 t-test 門檻（最近 64 次、上界 0.99）會在 push 到 main 的結果落在歷史區間外時讓該次執行失敗。

How to run the suite locally on macOS or Linux, filter benchmarks and compare baselines: BENCHMARKS.md.

在 macOS 或 Linux 本機執行、篩選 benchmark 與比較 baseline 的步驟見 BENCHMARKS.md。
